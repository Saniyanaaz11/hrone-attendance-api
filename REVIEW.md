# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 29-34) | The helper compares datetimes without applying the IST/overnight-shift rules, and it does not truncate instants to whole seconds before calculating. | A punch-in near midnight or at `09:40:00.900` for a `09:30` shift produces the wrong attendance day or late value; an overnight shift is calculated against the wrong calendar day. | Normalize instants to IST and whole seconds, determine the shift-start calendar date correctly, and calculate whole elapsed minutes with the 10-minute grace rule. |
| 2 | `compute_work_hours` (lines 36-37) | It uses binary floating-point `round`, which is banker's rounding rather than the required decimal half-up rounding. | A duration whose third decimal is exactly 5, such as a value that should report `4.50`, can be rounded incorrectly. | Use `Decimal` from the elapsed whole seconds and round with `ROUND_HALF_UP` to two decimal places. |
| 3 | `compute_overtime` (lines 40-43) | It always places the shift end on `date_str` and returns overtime for any positive amount; it does not handle overnight shifts or the required 30-minute minimum. | A `22:00-06:00` shift compares punch-out with 06:00 on the wrong day, and a punch-out 10 minutes after shift end incorrectly reports 10 overtime minutes instead of 0. | Build the shift end on the next day for overnight shifts and return overtime only when the elapsed time is at least 30 minutes. |
| 4 | `health` (lines 64-66) | It returns 200 without checking whether MongoDB is reachable. | Stop MongoDB and call `/health`; the endpoint still reports `{"status":"ok"}` instead of 503. | Ping MongoDB and return 503 with FastAPI's standard error body when the ping fails. |
| 5 | `EmployeeIn` and `create_employee` (lines 43-58, 69-77) | Employee fields and shift/date formats are not validated, `shift_start == shift_end` is accepted, and uniqueness is checked only with a non-atomic read. | Invalid times/dates are accepted; two concurrent requests with the same `emp_code` can both pass `find_one`; the database has no unique index to enforce the contract. | Add request validation, reject equal shift boundaries, create a unique `emp_code` index at startup, and translate duplicate-key errors to 409. |
| 6 | `create_employee` (lines 69-77) | `created_at` is stored as a naive datetime and is returned as an ISO datetime rather than epoch milliseconds. | The response does not match the contract's integer-millisecond representation, and timezone interpretation depends on the process/MongoDB settings. | Store a UTC-aware instant (or the repository's BSON UTC convention) and convert all API instants to/from epoch milliseconds. |
| 7 | `list_employees` (lines 80-88) | The skip calculation starts page 1 after the first page, `total` ignores the department filter, results are not sorted by `emp_code`, and page parameters are unrestricted. | Page 1 is empty/starts at the second page; a department-filtered response reports the global employee count; negative or oversized page values behave unexpectedly. | Validate `page >= 1` and `1 <= page_size <= 100`, use `(page - 1) * page_size`, count with the same filter, and sort by `emp_code` ascending. |
| 8 | `PunchInIn` and `punch_in` (lines 51-58, 91-116) | Employee absence causes a 500, timestamps are interpreted in the machine's local timezone, seconds/floats/strings are not rejected, values are not truncated to whole seconds, and status values are unrestricted. | Punching in for an unknown employee raises a server error; the same epoch value behaves differently on machines in different timezones; `status="INVALID"` is stored; a millisecond timestamp with sub-second precision is returned inconsistently. | Validate the employee and status, strictly validate epoch milliseconds, convert through UTC/IST as required, truncate to seconds, and return a clear 404/422 error. |
| 9 | `punch_in` (lines 96-116) | Duplicate prevention is a check-then-insert race, and there is no unique compound index on (`emp_code`, `date`). | Concurrent identical requests can create two attendance documents even though only one record is allowed per employee/date. | Create the compound unique index at startup and catch duplicate-key errors as 409. |
| 10 | `list_attendance` (lines 119-143) | It returns BSON datetimes in FastAPI's default ISO format instead of epoch milliseconds and does not normalize missing legacy fields such as `history`, `half_day`, or derived defaults. | The response violates the schema for `punch_in`, `punch_out`, and nested values; seeded legacy records have missing response fields. | Serialize every instant, including nested history change values, to integer milliseconds and supply the documented defaults without mutating the database document. |
| 11 | Contract endpoints are absent (lines 147-155) | Punch-out, correction, all analytics endpoints, and the admin explain endpoint are not implemented. | Requests to any listed path return 404, so the application cannot satisfy the OpenAPI contract or business rules R3-R10. | Implement each path with the specified request/response fields, validation, stored-derived-value behavior, correction history, pagination, and analytics rules. |

### Looked at but not considered defects

* `emp_code` is correctly used as the business identifier; MongoDB `_id` should not be exposed.
* `history` is initialized as an empty list at punch-in, which matches the rule that punch-in itself does not create an audit entry.
* `punch_out`, `work_hours`, and the other derived fields are initialized to their documented open-record defaults; they should be recalculated when the missing punch-out and correction endpoints are implemented.
