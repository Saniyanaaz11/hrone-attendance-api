# REVIEW.md

Defects found in the starter `app/main.py`, and what I did about them.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Never converts to IST: `punch_in.replace(hour=h, minute=m)` just takes whatever zone the datetime is in (server local time from `fromtimestamp`, or UTC from Mongo). It also truncates to whole minutes before comparing `> 10`, which breaks the strict 10:00 rule, and has no overnight handling (a punch-in after midnight gets that day's 22:00 start, not the previous day's). | Called with 09:40:01 it returns 0 (rule: 10), and 09:40:30 also returns 0. A UTC-aware 10:15:59 IST (04:45:59Z) returns 0, expected 45. It only looks right on a machine whose local time is IST. | Rewrote it. Converts to IST, works in seconds (`> 600`), returns floor(minutes since shift start), and uses the shared attendance-day helper so overnight shifts work. |
| 2 | `compute_work_hours` | `round()` on a float is banker's rounding plus float error, not half-up. | 16218 s = 4.505 h gives 4.5 (want 4.51). 450 s = 0.125 h gives 0.12 (want 0.13). 29250 s gives 8.12 (want 8.13). | `Decimal` division with `ROUND_HALF_UP`. |
| 3 | `compute_overtime` | No 30-minute minimum (`max(0, ..)` only). Builds shift end on the record date, so for an overnight shift it uses 06:00 on the start day, not the next day. Uses float division and truncation. | Shift end 18:30, out 18:45 returns 15 (rule: 0). Overnight 22:00-06:00, out 06:40 next day returns 1480 (rule: 40). | Integer floor of seconds, 30 minute threshold, shift end moved to the next day for overnight shifts. |
| 4 | `EmployeeIn` | No validation at all: any `emp_code`, bad `HH:MM`, `shift_start == shift_end`, junk `joined_on`, bad email. | POST `{"emp_code":"x","shift_start":"25:99"}` returns 201. | Pydantic patterns/lengths, a strict date check and a validator for equal shifts (422). |
| 5 | `create_employee` | Check-then-insert race, no unique index. `created_at` is naive local `datetime.now()` and is returned as a datetime, not epoch ms. | Two parallel creates both get 201. | Unique index on `emp_code`, rely on `DuplicateKeyError` -> 409. UTC whole-second `created_at`, serialized to epoch ms. |
| 6 | `list_employees` | `skip = page * page_size` skips the whole first page. `total` ignores the department filter. No sort. No limits on `page` / `page_size`. | Page 1 returns the second page of data. Filter by department and `total` is still everything. | `(page - 1) * page_size`, count with the same filter, sort by `emp_code`, `Query(ge=1, le=100)`. |
| 7 | `PunchInIn` / `punch_in` | `status` is any string. `punched_at` is a loose int (floats, seconds accepted) and `if body.punched_at` treats 0 as missing. | `"status":"BANANA"` is stored. A seconds timestamp becomes 1970. | `Literal` status, strict int in the epoch-ms range, `is not None` check. |
| 8 | `punch_in` | Unknown employee -> `emp` is `None` -> `TypeError` -> **500**. Uses `datetime.fromtimestamp` / `now()` in server local time, and `ts.date()` instead of the IST date. No overnight rule. Not truncated to seconds. Check-then-insert race. Response has an `id` and raw datetimes. | Unknown `emp_code` gives 500. Punch in at 00:30 IST gets the wrong date on a UTC server. Two parallel punch-ins both succeed. | 404 for unknown employee, UTC-aware timestamps, IST date + overnight rule (R1), unique `(emp_code, date)` index, 409 on duplicate, shared serializer (no `_id`/`id`, epoch ms). |
| 9 | `list_attendance` | `find(q)` loads the whole collection into a list and sorts in Python. Sort has no `emp_code` tie-break. No date validation, `date_from > date_to` not rejected, `status` unchecked. Leaks `id`, returns datetimes. | Slow and memory hungry at 100k docs. Ties come back in random order. | Database sort + skip/limit, `count_documents` with the same filter, indexes, validation (422), serializer. |
| 10 | Startup | No indexes at all. | Every list/analytics query is a COLLSCAN; explain shows it. | `create_indexes()` on startup, idempotent. |
| 11 | `health` | Always returns ok, even with MongoDB down. Client has no `serverSelectionTimeoutMS`. | Stop Mongo, `/health` still 200. | Pings Mongo, 503 on failure, 5s timeout. |
| 12 | `MongoClient(...)` | Not `tz_aware`, so reads return naive datetimes, while the helpers compare them with aware IST values and `punch_in` is stored from `datetime.now()` / `fromtimestamp` (server local time, not UTC). | `compute_overtime` with a naive `punch_out` raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. Stored times shift depending on the server's time zone. | `tz_aware=True`, all stored instants are UTC; `dt_to_ms` also treats a naive value as UTC as a safety net. |
| 13 | Whole file | Instants are returned as datetimes, not integer epoch ms; microseconds are never dropped (R1). | Response `punch_in` is an ISO string. | `ms_to_dt` truncates to seconds; `dt_to_ms` on the way out, also inside `history`. |

### Looked at but not considered defects

- `date` / `joined_on` as plain strings, compared with `$gte` / `$lte`. Fine: `YYYY-MM-DD` sorts the same as the calendar, and DATA_MODEL says to keep them as strings.
- Using `emp_code` instead of `_id` everywhere. That is the intended identifier.
- `doc.pop("_id")` in `create_employee`. It works, but I replaced it with a serializer that picks fields explicitly so `_id` can never leak.
- The 10 minute grace constant itself and the default shifts (09:30 / 18:30). They match the rules.
